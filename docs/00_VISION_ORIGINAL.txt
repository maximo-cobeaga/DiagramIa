# Producto: plataforma de diagramación AI-native

Quiero desarrollar una plataforma de diagramación visual comparable en alcance general a Draw.io, Miro, Excalidraw o Lucidchart, pero diseñada desde cero con una filosofía **AI-native**.

La idea central es que el usuario trabaje sobre un canvas completamente visual, pero que internamente todo el contenido exista como una representación estructurada en código.

El producto no debe tratar a la inteligencia artificial como un chatbot añadido encima de un editor gráfico tradicional. La IA debe formar parte del núcleo de la arquitectura.

## Concepto principal

El usuario ve:

- nodos
- cajas
- líneas
- conectores
- grupos
- diagramas
- texto
- imágenes
- iconos
- zonas
- animaciones
- flujos
- componentes
- diagramas técnicos
- diagramas libres

Pero internamente cada elemento está representado mediante un modelo estructurado propio, idealmente JSON o una DSL específica.

Por ejemplo:

```json
{
  "id": "postgres",
  "type": "database",
  "label": "PostgreSQL",
  "position": {
    "x": 840,
    "y": 320
  },
  "size": {
    "width": 160,
    "height": 80
  },
  "style": {
    "variant": "database",
    "theme": "blue"
  },
  "metadata": {
    "technology": "PostgreSQL"
  }
}
```

De esta forma, la IA no necesita interpretar el canvas únicamente mediante visión.

Puede entenderlo como una estructura semántica.

## Principio fundamental

La filosofía sería:

**Lo que el usuario ve es visual.  
Lo que el sistema entiende es código.**

Esto permite que cualquier modelo de IA compatible con structured output, function calling o generación de JSON pueda modificar el canvas.

La plataforma debería ser agnóstica respecto al proveedor de IA.

Debería poder integrarse con:

- OpenAI
- Anthropic
- Google Gemini
- modelos open-source
- modelos locales
- APIs compatibles
- futuros proveedores

El objetivo es evitar que el producto dependa exclusivamente de un único modelo.

# Chat lateral con IA

La aplicación tendría un chatbot lateral integrado al editor.

El usuario podría escribir instrucciones como:

- "Creá una arquitectura SaaS con React, Django, Redis y PostgreSQL."
- "Agregá un balanceador antes del backend."
- "Mové Redis debajo de la API."
- "Separá frontend, backend e infraestructura."
- "Simplificá este diagrama para mostrárselo a un cliente."
- "Animá el recorrido de una request."
- "Explicame este flujo paso por paso."
- "Convertí esta arquitectura a AWS."
- "Detectá puntos únicos de fallo."
- "Convertí este diagrama a Mermaid."
- "Creá documentación técnica a partir de este canvas."

La IA no debería devolver únicamente texto.

Debería producir acciones estructuradas sobre el canvas.

Por ejemplo:

```json
{
  "actions": [
    {
      "type": "ADD_NODE",
      "node": {
        "id": "redis",
        "type": "cache",
        "label": "Redis"
      },
      "placement": {
        "inside": "backend-zone",
        "below": "api"
      }
    },
    {
      "type": "ADD_EDGE",
      "from": "api",
      "to": "redis",
      "label": "cache"
    }
  ]
}
```

La aplicación valida las acciones y luego las ejecuta.

---

# IA observable

Un requisito importante es que la IA no modifique silenciosamente todo el canvas.

Quiero que el usuario pueda observar lo que está haciendo.

Por ejemplo:

1. La IA interpreta la solicitud.
2. Identifica los elementos involucrados.
3. Agrega un componente.
4. Lo posiciona.
5. Genera las conexiones.
6. Reordena los elementos afectados.
7. Actualiza el resultado final.

Idealmente, estas operaciones deberían verse progresivamente en pantalla.

También debería existir:

- undo
- redo
- historial
- versiones
- comparación de cambios
- revertir una acción de IA
- aceptar/rechazar cambios

---

# Canvas semántico

Una de las principales innovaciones sería introducir referencias semánticas dentro del canvas.

El usuario podría crear:

- zonas
- marcadores
- frames
- anchors
- regiones
- grupos
- referencias

Por ejemplo, utilizando una herramienta llamada **Marcador** o **Zona**, el usuario puede seleccionar una región del canvas y etiquetarla como:

- Backend
- Frontend
- Producción
- Base de datos
- Sistema externo
- Seguridad
- Flujo de autenticación
- Arquitectura actual
- Arquitectura futura

Internamente:

```json
{
  "id": "zone-backend",
  "type": "zone",
  "label": "Backend",
  "bounds": {
    "x": 400,
    "y": 200,
    "width": 600,
    "height": 400
  }
}
```

De esa forma, el usuario puede decir:

"Agregá Redis dentro de Backend."

La IA no necesita interpretar visualmente dónde está el backend.

El sistema sabe exactamente dónde se encuentra.

---

# Posicionamiento relativo

La IA no debería encargarse principalmente de decidir coordenadas absolutas.

En lugar de:

```json
{
  "x": 453,
  "y": 287
}
```

debería poder expresar:

```json
{
  "inside": "backend",
  "below": "api",
  "left_of": "postgres"
}
```

Después, un motor de layout transforma esas relaciones en coordenadas.

Esto debería mejorar sustancialmente la estabilidad de la generación automática.

---

# Selección contextual

Si el usuario selecciona elementos del canvas y luego habla con la IA, el sistema debería enviar esa selección como contexto.

Ejemplo:

El usuario selecciona:

- API
- Redis
- PostgreSQL

Y escribe:

"Ordená esta parte."

La IA recibe:

```json
{
  "selected_elements": [
    "api",
    "redis",
    "postgres"
  ]
}
```

Esto elimina una gran cantidad de ambigüedad.

También debería funcionar para:

- nodos individuales
- grupos
- regiones
- conexiones
- frames
- flujos completos

---

# Sistema de acciones

La IA no debería editar directamente el documento completo siempre que sea posible.

Debería utilizar un conjunto controlado de operaciones.

Ejemplos:

- ADD_NODE
- DELETE_NODE
- UPDATE_NODE
- MOVE_NODE
- RESIZE_NODE
- ADD_EDGE
- DELETE_EDGE
- UPDATE_EDGE
- CREATE_ZONE
- CREATE_GROUP
- GROUP_NODES
- UNGROUP_NODES
- UPDATE_STYLE
- CREATE_ANIMATION
- MOVE_TO_ZONE
- ALIGN
- DISTRIBUTE
- AUTO_LAYOUT
- ADD_LABEL

Esto permite:

- validación
- seguridad
- historial
- undo
- observabilidad
- compatibilidad entre modelos

# Animaciones

El producto no debería limitarse a diagramas estáticos.

Quiero soportar animaciones y secuencias.

Por ejemplo:

"Mostrame cómo funciona el login."

El sistema podría generar:

1. Usuario envía credenciales.
2. Frontend envía request.
3. API valida datos.
4. Auth service genera token.
5. PostgreSQL devuelve información.
6. Token vuelve al usuario.

Visualmente podrían animarse:

- líneas
- partículas
- nodos
- estados
- colores
- resaltados
- etiquetas
- zoom
- cámara

Las animaciones también deberían representarse en código.

Ejemplo:

```json
{
  "animation": {
    "id": "login-flow",
    "steps": [
      {
        "highlight": "user"
      },
      {
        "flow": {
          "from": "user",
          "to": "frontend"
        }
      },
      {
        "flow": {
          "from": "frontend",
          "to": "api"
        }
      }
    ]
  }
}
```

# AI-friendly by design

Todo el producto debería estar diseñado pensando en que una IA pueda entenderlo fácilmente.

Esto implica:

- IDs estables
- esquema documentado
- nombres semánticos
- relaciones explícitas
- posiciones relativas
- metadata
- agrupación
- jerarquías
- selección
- zonas
- referencias
- versionado
- acciones deterministas

Un diagrama debería poder describirse con una estructura relativamente compacta.

Ejemplo:

```json
{
  "zones": [...],
  "nodes": [...],
  "edges": [...],
  "animations": [...],
  "selection": [...]
}
```

# Diferencia respecto de Draw.io

No quiero construir simplemente una alternativa visual más moderna a Draw.io.

La diferencia fundamental debería ser:

**Draw.io permite dibujar diagramas.**

Este producto debería permitir:

**crear, entender, transformar, explicar, revisar y animar diagramas mediante inteligencia artificial.**

La IA debe poder operar sobre el diagrama como si estuviera trabajando con código.

# IA como analista

La IA debería poder analizar un diagrama, no solamente modificarlo.

Por ejemplo:

"Revisá esta arquitectura."

Y responder:

- existe un posible single point of failure
- Redis no tiene redundancia
- no existe sistema de observabilidad
- falta estrategia de backups
- la base de datos está expuesta directamente
- no existe rate limiting

Las observaciones podrían aparecer directamente sobre el canvas.

# Modelo de IA gratuito

Quiero incluir una capa gratuita de IA dentro del producto.

No debería ser IA ilimitada.

La estrategia inicial podría ser:

Free:

- modelo económico
- cantidad limitada de prompts diarios
- contexto limitado
- generación de diagramas pequeños
- edición básica
- explicación básica

Pro:

- modelos superiores
- contexto mayor
- diagramas grandes
- auditoría
- animaciones
- documentación
- integraciones
- mayor cantidad de prompts

El backend debe abstraer el proveedor.

Arquitectura aproximada:

```text
Canvas
↓
AI Orchestrator
↓
Context Builder
↓
LLM Router
↓
Structured Actions
↓
Validator
↓
Canvas Engine
```

Esto permitiría cambiar fácilmente entre OpenAI, Gemini, Claude, modelos locales u otros proveedores.

# Hipótesis central del producto

Los diagramadores actuales fueron diseñados principalmente para humanos y posteriormente recibieron funciones de IA.

Este producto debería diseñarse desde el comienzo para que humanos e IA puedan operar sobre la misma representación.

El humano trabaja visualmente.

La IA trabaja estructuralmente.

Ambos modifican el mismo documento.

Por eso considero conceptos como:

**Semantic Canvas**

**Diagram-as-Code**

**AI-native Canvas**

**Living Diagrams**

como formas adecuadas de explicar la filosofía del producto.
